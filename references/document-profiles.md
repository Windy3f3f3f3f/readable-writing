# 文档类型与发布门禁

句子自然不等于文档写对了。动笔前先选一种主要文档类型；若同时承担两种用途，明确主次，不要把
口头串词、技术分享、项目交接和平台需求混成一篇。

## 共同门禁

写正文前回答四个问题：

1. 谁读：算法同行、研发协作者、导师、业务方还是接手 Agent？
2. 读完做什么：理解方法、复现流程、判断结果、接手任务还是拍板？
3. 主证据是什么：论文、代码、运行产物、平台回读、业务数据还是案例？
4. 不写什么：个人身份、未验证展望、平台需求、敏感样本还是旁支背景？

只读标题、摘要、各节第一句和结尾，应该能复述完整故事。详细正文负责证明这条故事线，不负责
另起一条线。

## 发布成稿门禁

先判断交付物是工作记录还是发布成稿。`progress/`、迭代记录、实验台账和故障记录可以保存
调查过程、工具限制、复核发现、待办和中间结果；面向同事、合作者或公开读者的报告、分享稿、
说明文档默认不保存这些会话现场。

### 成稿不是工作日志

发布正文通常删除：

- `Plan / Done / Pending / TODO` 等执行清单；
- “本轮没有创建子 Agent”“当前工具策略要求”等 Agent 运行说明；
- “本次只修改了”“用户确认后再做”等会话状态；
- 与读者理解结论无关的调试过程、临时 Task/Job、复核流程和内部运行记录。

过程若解释了方法、结果来源或失败机制，可以转写成读者需要的事实；不要原样搬运 Agent 的工作日志。

### 写给独立读者

做一次“脱离对话测试”：不了解当前聊天、也不知道“用户”指谁的人，能否直接读懂？

- 不写“按你的要求”“这里给你解释”“我们刚才讨论了”“待用户确认”。
- 不向读者汇报 Agent 做了什么；直接写系统、实验、证据和结论。
- 需要用户拍板的事项留在聊天、`HUMAN.md` 或 progress，不混进发布正文。
- 第一人称只有在作者的真实决策、观察或经验本身就是内容时才保留。

### 最终证据优先

- 发布稿优先使用最终报告、正式 Evaluation、稳定 Wiki 或正本产物。
- 本地草稿、探索性 JSON、中途 checkpoint 和未闭合实验不能冒充项目最终结论。
- 中间结果只有在文档本身是状态报告时才进入正文，并写清测量窗口和当前阶段。
- 最终结果尚未形成时，优先写内部进度记录；不要先产出一份外观像正式结论的发布稿。

### 严谨但不自我免责

过度防御的典型表现是每个判断后都补“仅能说明、不能证明、仍需注意、尚未验证、不能替代”。
必要边界要保留，但只留会改变读者判断或行动的限制：

- 先在证据支持的范围内直接下结论，再补最近的一条适用边界。
- 同一限制不在摘要、结果、解读和结尾重复。
- 工具权限、Agent 行为和“本轮没做什么”通常不是业务限制。
- 不能改变结论的常规免责声明删掉；真正重要的分母、样本范围、未验证场景紧跟结果写清。

坏例：

> 本结果仅基于当前样本，尚不能证明线上收益，也不能替代正式评测，后续仍需进一步验证。

好例：

> 在这批 1,000 条 hardcase 上，漏放率从 31% 降到 24%。线上自然分布尚未评测。

## 技术分享稿

适用于算法团队 Markdown/飞书技术分享。资料研究和事实核查交给 `paper-share-talk`；
本节只约束最终叙事和中文表达。

### 动笔前

- 核对准确论文、版本和主讲对象；同一机构的近邻论文不能凭印象代替。
- 用户要求先讨论时，先给 5–7 条故事线、主次材料和篇幅分配，确认后再写全文。
- 主体放在用户真实做过或已验证的方向；未来工作只作收尾。

### 故事结构

推荐顺序：

```text
核心矛盾或反直觉结果
→ 现有方法为什么不够
→ 主讲方法的输入、输出和关键机制
→ 实验、消融和失败边界
→ 与内部事实的对照
→ 能带走的判断和下一步
```

- 面向专业听众，不用论文证明团队已经知道的常识。论文只有带来新机制、协议或反直觉结果时
  才占主讲篇幅。
- 一篇主论文或一个主方法要讲深；产品游览、同类工作时间线和业务方案只能服务主线。
- 内部案例用于检验外部方法是否成立，不要让论文沦为业务方案的脚注。
- 每个一级章节先给一句“本章结论”。飞书可用提示块；Markdown 用普通引用块即可。
- 图放在对应分析旁边，图后立刻解释它证明什么，不把关键图堆在附录。
- 长稿之外附 3–5 句“核心记忆”：主问题、方法差异、关键结果、适用边界。

### 书面稿边界

- 去掉“我是实习生”“我为什么选这个题”等个人定位。书面稿围绕方法、证据和结论。
- 口头开场、时间提示和现场互动另存讲稿备注，不混进正文。
- 若团队惯例是 Markdown，不按 PPT 的“一页一个点”切碎全文。

## 研发交接与流程讲解

目标是让协作者理解当前系统怎样工作并能继续追踪，不是替研发写平台需求。

### 必须回答

1. 设计原理：为什么这样拆，解决什么约束。
2. 代码文件：每个阶段的真实入口在哪里。
3. 运行平台：本地、Dorado、Merlin、服务或其他平台各负责什么。
4. 提交任务：代码怎样渲染为提交参数，最终由什么命令或节点提交。
5. 验收与 Eval：如何判断数据、训练、checkpoint、服务或业务结果真的完成。

可用一张表把链路写实：

| 阶段 | 代码入口 | 运行平台 | 输入/输出 | 完成证据 |
|---|---|---|---|---|

- 写当前流程“实际上怎样跑”，不要写成“平台应该新增什么能力”。
- 若已有强且当前的正本文档，先核数并复用，不另写一份会漂移的平行版本。
- 路径、分支、Task/Job 和数字来自当前正本；名字看着像也要回读。
- 对外包或跨团队交付时，删除敏感数据和内部运行记录，但保留正文明确引用的代码，避免“安全
  处理”后文档无法复现。

## 口头介绍稿

口头稿要帮主讲人讲，不是把正式报告换个标题。

- 开头先用 30–60 秒讲结论和全链路，让听众知道后面为何展开。
- 使用“我先讲什么、为什么、接下来怎么看”的自然过渡，但不要每节重复“下面介绍”。
- 只保留必要的第一人称，用于说明真实决策和协作过程；个人身份和资历不写。
- 数字表格可以留在正文，口头提示另写成简短的讲稿备注。
- 预计时长要绑定章节，不要把所有材料平均分配。

## 单页说明与架构说明

单页说明只承担一个判断。推荐四块：

1. 问题和边界；
2. 架构或流程分工；
3. 当前结果与证据；
4. 风险、状态和下一步。

- 明确哪些阶段是确定性 API/并发任务，哪些阶段是迭代 Agent，不把整个平台统称为 Agent。
- 架构图中的箭头必须对应真实数据流或控制流；图下用两三句话解释关键分工。
- 一页放不下时，主文仍保持单页摘要，细节通过链接进入专题文档。

## 进度与研究报告

沿用 `positive-style.md` 的结论先行和证据纪律。额外注意：

- 业务汇报与研究评测分开，不能用一个口径替代另一个。
- 结果通常先讲结论，再交代数据与抽样、方法、指标和结果，最后解释失败簇并给出建议；不要为了
  模板完整硬凑空章节。
- 负面结果、限制和未完成状态要与成功结果同等可见。

## 交付载体边界

- 飞书原生块、附件保留、Wiki 节点和权限由 `lark-doc`/`lark-wiki` 处理；本 Skill 只给内容结构。
- PPT 的页面设计和可编辑图形由 `report-ppt` 或 `paper-share-talk` 处理。
- 论文身份、引用、图表和事实账本由 `paper-share-talk` 或论文写作 Skill 核验。
- 若用户只要一段核心记忆，直接给 3–5 句，不强迫对方先读完整报告。
